      Part 1 · Mental model
      
WITH RECURSIVE — Anchor · Step · Stop

      

        A recursive CTE is two queries glued with UNION ALL:
        the anchor seeds row set pass 0;
        the recursive step joins new rows to the growing result;
        stop when the step returns nothing—or when your WHERE depth < N guard blocks cycles and runaway depth.

    Anchor
    Fixed starting set—roots, start date, or seed row.
    
        
    Step
    Join the working set to source rows; append new rows.
    
        
    Stop
    No new rows, or depth < N fails.

      Part 2 · Theory
      
    Query optimization architecture
    
      
    
        There are two common worlds: OLTP (apps saving one order or login at a time) and OLAP (reports scanning huge history in S3). Some habits help both; others only fit one world. The poster below is the map—cards explain it in plain language.
      
    
      
    Golden rule: OLTP speeds up finding one row; OLAP speeds up skipping files and columns you do not need.
    
      

      
    
        
        
        
        
      
    

      
    
        
    
          
    
            
    Workload first
    Classify read/write pattern, latency target, and data volume before touching indexes or file layout.
    
            
    Measure, then change
    Capture baseline duration and row counts; change one variable; re-measure.
    
            
    OLTP
    Checkout, CRM, banking—fast lookup by id, many small writes.
    
            
    OLAP
    Dashboards and lake SQL—read big history, touch few columns and folders.
    
          
    
        
    
        
    
          
    Good habits on PostgreSQL and Athena.
    
          
    
            
    Filter-friendly WHERE
    Compare the column itself to a value—order_date >= '2026-01-01'. Avoid YEAR(order_date) = 2026; wrapping the column often blocks shortcuts.
    
            
    Filter before join
    Use WHERE to shrink rows before big JOINs and GROUP BY—less work for the engine.
    
            
    Avoid duplicate explosion
    Join on the right keys at the right grain. If rows multiply, fix the join—don't paper over it with DISTINCT on a huge result.
    
            
    Only columns you need
    List columns in SELECT. Skip SELECT * on wide tables—especially on lakes with dozens of fields.
    
          
    
        
    
        
    
          
    Typical engines: PostgreSQL, MySQL, SQL Server. Data stored row by row—great for “fetch order #12345.”
    
          
    
            
    Indexes (lookup shortcuts)
    Like a sorted phone book on order_id—jump to one row instead of reading every row in the table.
    
            
    Index holds extra columns
    If the index already stores every column your query needs, the engine may never open the main table at all.
    
            
    Reusable query templates
    Apps send the same SQL shape with different ids (WHERE order_id = ?) so the database doesn't re-plan from scratch every click.
    
            
    Tidy tables, small locks
    Store each fact once (normalized). Updates touch one row; other users' rows stay unlocked.
    
          
    
        
    
        
    
          
    Typical engines: Athena, Redshift, Databricks. Files on S3, often column by column—great for “sum revenue last year.”
    
          
    
            
    Read columns you asked for
    Parquet stores each column separately. Need amount and date? The engine can ignore the other 48 columns in the file.
    
            
    Skip whole folders
    Data lives in paths like month=11/. Filter to November and Athena never opens October's files.
    
            
    Related data stored together
    When files are sorted by date (or similar), the engine can skip big chunks whose min/max doesn't match your filter.
    
            
    Avoid moving too much data
    Huge joins shuffle rows across machines—that's slow. Sometimes an approximate distinct count (APPROX_DISTINCT) is enough for a dashboard.
    
          
    
        
    
      
    
    
    

    

  
    
    
    
      Recursion practice
      
    WITH RECURSIVE — easy / medium / hard
    

      
    
        
    E · Reversed join (walks the wrong way)
    
        
    
          Input — linear chain: Aarav (1) → Diya (2) → Kabir (3) → Meera (4), same as day06_employees.
        
    
        
    
          Problem: Anchor: WHERE mgr_id IS NULL (CEO only). Recursive join is mistakenly written as ON e.emp_id = t.mgr_id instead of ON e.mgr_id = t.emp_id. After the recursive CTE finishes, how many rows are in the result, and who appears?
        
    
        
    Expected output — final row set:
    
        
    
          
    
            
    emp_idname
    
            
              
    1Aarav
    
                
          
    
        
    
        
    
          Answer
          
    Pass 0 still adds Aarav. On pass 1 the bad join looks for employees whose emp_id equals Aarav's mgr_id—but mgr_id is NULL, so no row matches. The recursive step returns zero new rows and the CTE stops with one row only. To walk down to reports, the child's mgr_id must equal the parent's emp_id.
    
        
    
      
    

      
    
        
    M · Walk up the chain from Meera
    
        
    
          Input — same four-employee table.
        
    
        
    
          Problem: Build WITH RECURSIVE mgr_chain that starts at emp_id = 4 (Meera) and climbs to the CEO. Recursive join: e.emp_id = t.mgr_id (parent row = employee who manages current row). Return name, steps_up (1 = Meera, 2 = her manager, …), ordered by steps_up.
        
    
        
    Expected output:
    
        
    
          
    
            
    steps_upname
    
            
              
    1Meera
    
              
    2Kabir
    
              
    3Diya
    
              
    4Aarav
    
                
          
    
        
    
        
    
          Answer
          
    
            
    Anchor: Meera with steps_up = 1.
    
            
    Step: from Meera (mgr_id = 3) pull Kabir; from Kabir pull Diya; from Diya pull Aarav; Aarav's mgr_id is null so the next pass adds nobody.
    
            
    Same machinery as walking down—only the join direction and anchor row change. Useful for “who is this person's skip-level manager?” without a fixed-depth self-join.

          Input A — org with two branches under the CEO:
        
    
        
    
          
    
            
    emp_idnamemgr_id
    
            
              
    1AaravNULL
    
              
    2Diya1
    
              
    3Kabir1
    
              
    4Meera2
    
              
    5Isha3
    
                
          
    
        
    
        
    
          Part 1: Recursive walk down from CEO with correct join e.mgr_id = t.emp_id. How many rows, and what is the maximum depth?
        
    
        
    
          Input B — date spine Nov 1–5 exists; sales only on Nov 1 and Nov 3 (same pattern as class data).
        
    
        
    
          Part 2: Someone uses INNER JOIN daily_sales on the spine instead of LEFT JOIN. How many rows come back, and which dates disappear from the report?
        
    
        
    Expected answers (summary):
    
        
      
          
    • Part 1: 5 rows; max depth 2 (Meera and Isha under different VPs).
      • 
          
    • Part 2: 2 rows (Nov 1 and Nov 3 only); Nov 2, 4, 5 vanish—dashboards look “healthy” but daily totals are wrong.
      • 
        
    
        
    
          Answer
          
    
            
    Part 1: Pass 1 adds Diya and Kabir (both report to Aarav). Pass 2 adds Meera (under Diya) and Isha (under Kabir). No depth-3 rows exist, so recursion ends. A single chain assumption (like our four-row lab table) would miss Isha entirely.
    
            
    Part 2: The spine still generates five dates, but inner join keeps only dates with a matching sale. Zero-sale days never appear—so 7-day moving averages and “days since last sale” metrics break. The fix is LEFT JOIN + COALESCE(revenue, 0) on the spine side.
