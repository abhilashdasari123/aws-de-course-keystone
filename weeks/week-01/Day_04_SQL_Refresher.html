Module 0

What is SQL—relational building blocks

SQL (Structured Query Language) is the shared language for reading and shaping relational data: rows and columns linked by keys. Athena, Redshift, Spark SQL, and dbt use the same core ideas—SELECT, JOIN, GROUP BY—even when the “database” is really files on S3 plus a catalog (Glue).

SQL is declarative: you describe what result you want; the engine chooses how to scan, join, and aggregate. As a data engineer you care about correct grain, join keys, and filters in the right clause (WHERE vs HAVING) so pipelines and ad hoc queries stay trustworthy.

Table, row, column

  • Table — one entity (orders, customers). In the lakehouse it is often a folder of Parquet/CSV files.
  • Row — one record (a single order).
  • Column — one attribute (order_status, price).
  • Grain — what one row means (per order vs per line item).

Keys & relationships

  • Primary key (PK) — unique ID for a row (order_id).
  • Foreign key (FK) — column that points to another table’s PK (customer_id on orders).
  • JOIN — combine tables on matching keys (customer → orders).
  • NULL — “unknown / not applicable”—not zero, not empty string.

Lakehouse vs classic DB

  • Storage — objects in S3 (Parquet, CSV), not rows inside a single server disk.
  • Catalog — Glue table name + column types tell Athena what to read and how.
  • Query — you still write SQL; the engine pushes work down to scan files.
  • Today — shared read-only tables in de_keystone_shared; your workgroup writes results elsewhere.

What you do with SQL as a DE

Explore

Ad hoc SELECT in Athena to validate data, counts, and joins before you ship a pipeline.

Transform

CREATE TABLE AS SELECT, inserts, or dbt models that build curated layers from raw or staging tables.

Register

CREATE EXTERNAL TABLE (instructor/admin) so Parquet/CSV paths become queryable names in the catalog.

Data engineering angle: your job is to write SQL (or Spark) that respects grain and keys so metrics are not double-counted when tables are joined. Dialects differ in functions and types—always check Glue types match Parquet before blaming the query.

Module 1

SQL clauses—what each keyword does

You write queries top-to-bottom like English, but the engine runs them in a different order (Module 4). Learn the vocabulary first.

SELECT

Which columns or expressions appear in the result (including CASE, COALESCE).

FROM

Which table(s) to read—on Athena, Glue table names or S3-backed external tables.

JOIN

INNER keeps matches only; LEFT keeps all left rows.

WHERE

Filter rows before grouping—cannot use SELECT aliases here.

GROUP BY

Collapse rows into buckets for COUNT, SUM, AVG.

HAVING

Filter groups after aggregation (e.g. revenue > 10k).

ORDER BY

Sort final output; can use SELECT aliases.

LIMIT

Cap rows returned—great for labs; in prod, prefer filters/partitions.

NULL handling

IS NULL / IS NOT NULL for missing data—see Lab 2 for COALESCE and CASE WHEN in full.

Module 4

SQL logical order of execution

Why WHERE ≠ SELECT aliases

WHERE filters before SELECT computes aliases. Reference expressions again or use a subquery/CTE.

Why HAVING follows GROUP BY

HAVING filters aggregated buckets (e.g. SUM(price) > 10000). WHERE cannot see those sums.

      Hands-on · Lab 2
      
NULL handling with COALESCE & CASE WHEN


      

        
Problem statement

        

          Business context: The Olist logistics team wants a quick delivery SLA report for orders placed from 2017 onward. Operations needs one row per order with a human-readable label: early, late, on time, in transit, or canceled—not raw timestamps scattered across nullable columns.
        

        
    
          
  • Source table: de_keystone_shared.olist_orders (Parquet on S3: olist/parquet/orders/).
    • 
          
  • Scope filter: Only orders with order_purchase_timestamp >= TIMESTAMP '2017-01-01'.
    • 
          
  • NULL rule: Many rows have NULL order_delivered_customer_date (still shipping or canceled). Build effective_delivery_ts using COALESCE(actual, estimated) so you still have a timestamp to reason about when actual delivery is missing.
    • 
          
  • Classification rule: Add column delivery_sla with CASE WHEN:
            
      
              
    • canceled / unavailable → 'In Transit / Canceled'
      • 
              
    • NULL actual delivery date → 'In Transit / Canceled'
      • 
              
    • Actual < estimated → 'Delivered Early'
      • 
              
    • Actual > estimated → 'Late'
      • 
              
    • Otherwise → 'On Time'
      • 
            
    
          
    • 
          
  • Required output columns: order_id, customer_id, order_status, order_purchase_timestamp, effective_delivery_ts, delivery_sla.
    • 
          
  • Presentation: Order by purchase time ascending; return 20 rows (LIMIT 20) for inspection in Athena.
    • 
        

        
Done when: query runs in your workgroup, NULLs do not break comparisons, and delivery_sla has no unexpected NULLs.

      


      
 What these two expressions do (same lab)

      

        

          
COALESCE

          
Returns the first non-NULL argument left to right.

          
COALESCE(
  actual_delivery_ts,
  estimated_delivery_ts
) AS effective_delivery_ts

          
If the customer delivery date is NULL, fall back to the estimated date so downstream logic still has a timestamp to compare.

        

        

          
CASE WHEN

          
SQL’s if / else—evaluates conditions top to bottom and returns the first match.

          
CASE
  WHEN order_status IN ('canceled','unavailable')
    THEN 'In Transit / Canceled'
  WHEN delivered_ts < estimated_ts
    THEN 'Delivered Early'
  WHEN delivered_ts > estimated_ts
    THEN 'Late'
  ELSE 'On Time'
END AS delivery_sla

          
Handle status and NULLs before comparing dates—otherwise NULL < date stays unknown.

Lab 3 — Parquet chain + CSV translation + anti-join


      

        
Problem statement

        

          Business context: Customer experience wants to prioritize delivered orders that never received a review—those customers were not asked (or did not respond), but the order completed. Merchandising also wants each row enriched with line-item counts, order GMV, and an English product category name for outreach templates.
        

        
    
          
  • Join path (inner chain):
            olist_orders → olist_order_items → olist_products on the usual keys (order_id, product_id).
    • 
          
  • Cross-format join: LEFT JOIN olist_category_translation (CSV in S3) on product_category_name to populate product_category_name_english.
    • 
          
  • Reviews (anti-join): LEFT JOIN olist_order_reviews on order_id, then keep only rows where review_id IS NULL—delivered orders with no review record.
    • 
          
  • Row filter: order_status = 'delivered' (apply in WHERE, before grouping).
    • 
          
  • Aggregates per order: COUNT(DISTINCT order_item_id) as item_count; ROUND(SUM(price), 2) as order_gmv. Group by order, status, English category, and review fields so one row per order in the result.
    • 
          
  • Sort & limit: Highest GMV first; show top 25 orders for the CS queue.
    • 
        

        
Done when: every row is a delivered order with null review, category names read in English, and GMV matches the sum of line items for that order.

      


        

          
          

        


      
Lab 4 — Category revenue rollup with HAVING


      

        
Problem statement

        

          Business context: The category management team is planning a promotions budget. They need a rollup of product categories (English labels) ranked by revenue—but only categories that materially contributed to sales, not long-tail noise.
        

        
    
          
  • Grain: One output row per product_category_name_english (after joining items → products → CSV translation, same chain as Lab 3).
    • 
          
  • Metrics to compute:
            
      
              
    • COUNT(DISTINCT o.order_id) — number of distinct orders (not line items).
      • 
              
    • SUM(oi.price) — total item revenue in the category (rounded to 2 decimals).
      • 
              
    • AVG(oi.freight_value) — average shipping cost per line item (rounded).
      • 
            
    
          
    • 
          
  • Group filter: Use HAVING SUM(oi.price) > 10000 so only categories with more than R$10,000 total item revenue appear—this cannot go in WHERE because it is an aggregate.
    • 
          
  • Sort: Descending by total revenue so leadership sees top categories first.
    • 
          
  • No row limit: Return all categories that pass the HAVING threshold.
    • 
        

        
Done when: row count drops after HAVING, category names are English, and distinct_orders does not inflate because of the items join.

The team wants to intervene with training or delisting— but seller-level metrics must be computed at the correct grain so multi-item orders and multi-review rows do not distort averages.

    •

    • 
          
  • Output columns: seller_id, delivered_orders, avg_review_score (rounded).
    • 
          
  • Ranking: Return the top 5 sellers with the lowest average review scores; break ties by higher delivered order volume.

Interview practice

      
Day 4 focus: SQL execution order, joins, grain, and NULL handling. Answer in under 90 seconds.

      

        
E · Explain the difference between WHERE and HAVING.

        

          Reveal strong answer
          
WHERE filters individual rows before GROUP BY—only non-aggregated columns allowed. HAVING filters groups after aggregates exist (SUM, COUNT, AVG). WHERE SUM(amount) > 100 is invalid; that condition belongs in HAVING. Order: FROM → joins → WHERE → GROUP BY → HAVING → SELECT → ORDER BY.

        

      

      

        
M · Second-highest salary (no window functions)

        

          
Table employees(emp_id, name, salary):

          

            

              
emp_idnamesalary

              
                
1Alice90000

                
2Bob120000

                
3Carol120000

                
4Dan75000

              
            

          

          
Write SQL to return the second-highest salary value (here: 90000). Do not use ROW_NUMBER, RANK, or DENSE_RANK.

        

        

          Reveal strong answer
          
SELECT MAX(salary) AS second_highest_salary
FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);

          
Nested MAX finds the top distinct level below the maximum (handles ties at the top). Alternative: ORDER BY salary DESC OFFSET 1 LIMIT 1—returns one row at the second position, not always the same as “second distinct salary” when ties exist.

        

      

      

        
H1 · Why can NOT IN return no rows when NULL is in the list?

        

          
departments_active(dept_id) contains 10, 20, NULL.

          
You filter employees with:

          
WHERE dept_id NOT IN (SELECT dept_id FROM departments_active)

          
Why might you get zero rows even when employees exist whose dept_id is neither 10 nor 20?

        

        

          Reveal strong answer
          
What actually happens: col NOT IN (v1, v2, …) means col <> v1 AND col <> v2 AND … for every value in the list (literals or subquery rows). That is standard SQL three-valued logic—same in Athena, PostgreSQL, SQL Server, Oracle, and MySQL; not table-format or engine-specific.

          
If the list is (10, 20, NULL) and dept_id = 99, SQL evaluates 99 <> 10 AND 99 <> 20 AND 99 <> NULL. The first two parts are true, but 99 <> NULL is UNKNOWN (not TRUE—comparisons to NULL never yield TRUE/FALSE). With AND, if any part is UNKNOWN, the whole condition is not TRUE, so WHERE drops the row. One NULL in the subquery can therefore empty the result for every employee, even those not in 10 or 20.

          
Fixes: WHERE NOT EXISTS (SELECT 1 FROM departments_active d WHERE d.dept_id = e.dept_id), or WHERE dept_id NOT IN (SELECT dept_id FROM departments_active WHERE dept_id IS NOT NULL).

        

      

      

        
H2 · Earnings above your department average

        

          
employees(emp_id, name, dept_id, salary)—list employees who earn strictly more than the average salary in their own department (not the company-wide average).

        

        

          Reveal strong answer
          
SELECT e.emp_id, e.name, e.dept_id, e.salary
FROM employees e
WHERE e.salary > (
    SELECT AVG(e2.salary)
    FROM employees e2
    WHERE e2.dept_id = e.dept_id
);

          
Inner query is correlated—re-evaluated per outer row. A single global AVG(salary) answers a different question.

        

      

      

        
H3 · Customers with repeat orders on different days

        

          
orders(order_id, customer_id, order_date)—find customer_id values who placed at least two orders on different calendar dates.

        

        

          Reveal strong answer
          
SELECT DISTINCT a.customer_id
FROM orders a
INNER JOIN orders b
    ON a.customer_id = b.customer_id
   AND a.order_id < b.order_id
WHERE a.order_date <> b.order_date;

          
order_id ordering picks one pair per two orders once; date inequality enforces different days. HAVING COUNT(*) > 1 alone does not require different dates.
