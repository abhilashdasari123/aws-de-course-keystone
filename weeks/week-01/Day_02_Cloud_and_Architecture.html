Module 2

ETL vs ELT

The letters are the same—only the order changes. ETL: Extract → Transform → Load (transform before the destination sees data). ELT: Extract → Load → Transform (land data first, transform inside the lake or warehouse). Neither is “wrong”; the fit depends on compliance, source constraints, and where you want compute to run.

ETL pipeline

Data is cleansed, filtered, and conformed on a staging or ETL engine, then loaded into the target warehouse or mart.

  • Fits strict compliance: sensitive fields masked before storage.
  • Legacy warehouses with limited compute—do heavy work off-platform.
  • Trade-off: rule changes often mean re-extract from sources.

ELT pipeline

Raw files land in S3 (or the lake) immediately; Glue, Athena, or Redshift run transforms at scale in the cloud.

  • Handles large volume and mixed formats (CSV, JSON, logs) cheaply.
  • Analysts iterate on SQL without re-hitting operational databases.
  • Matches Bronze → Silver → Gold: keep history, replay transforms.

When to choose ETL vs ELT

Use this as a design checklist—not a brand preference. Many production platforms mix both.

Prefer ETL when…

  • ①Compliance before storage — regulations or policy require masking, tokenizing, or filtering PII/PHI before data lands in a shared lake or third-party region.
  • ②Weak destination compute — legacy warehouse or RDBMS that should receive narrow, already-typed tables, not raw JSON or wide dumps.
  • ③Expensive or slow links — you pay per GB moved; shrinking and filtering at a staging tier reduces load size and recurring sync cost.
  • ④Stable, structured sources — a small set of relational schemas with predictable contracts; transforms are versioned with the warehouse release, not explored ad hoc.
  • ⑤Strict access boundaries — only curated rows may exist in the analytics zone; raw extracts must not be discoverable by downstream tools.

Watch out: KPI or schema changes often force a re-extract unless you also keep a raw archive elsewhere.

Prefer ELT when…

  • ①Elastic cloud compute — the lake or warehouse (Spark, SQL engine) is built to scan and transform at scale; you pay for queries, not a fixed ETL fleet.
  • ②Volume and variety — event streams, logs, APIs, and nested JSON where schema emerges over time; load first, enforce structure in Silver.
  • ③Medallion / lakehouse — Bronze must stay immutable; Silver and Gold are recomputable views and jobs on top of that history.
  • ④Fast time-to-data — stakeholders need yesterday’s files available today; refinement can follow on a schedule or micro-batch.
  • ⑤Many consumers, one raw copy — finance, ops, and ML each run different transforms without hammering the same OLTP source.

Watch out: raw zones need governance (access, encryption, retention) because sensitive data may exist until Silver jobs run.

Hybrid pattern (common in practice)

Lightweight ETL at the edge (field redaction, virus scan, format validation) → bulk ELT in the platform (dedupe, joins, Gold KPIs). Example: tokenize patient IDs in an ingest function, then run Glue or warehouse SQL for clinical metrics. Interview sound bite: “We ETL what must never land raw; we ELT everything we might need to replay.”

Module 3

AWS data engineering ecosystem

End-to-end flow: ingest from databases, SaaS, and streams → store in the lake with governance → transform and orchestrate pipelines → analyze with SQL and search → consume in BI, ML, and apps.

1 · Ingest

Move data from on-prem, applications, IoT, and SaaS into AWS without overloading sources.

AWS DMS

Replicates OLTP and NoSQL databases to AWS with minimal downtime. Use for lift-and-shift, CDC into Bronze, or ongoing sync instead of nightly bulk dumps.

Amazon Kinesis & MSK

Ingest high-volume event streams (clicks, logs, device telemetry). Kinesis for managed streams; MSK when you need Apache Kafka compatibility and ecosystem tools.

AWS DataSync

Accelerates file and object copies from NAS or on-prem storage into S3. Use for large historical file migrations and recurring folder sync.

Amazon AppFlow

Pulls or pushes SaaS records (Salesforce, Marketo, Slack, etc.) into S3 or other targets. Use for connector-style SaaS ingestion without custom API code.

2 · Store

Durable lake storage plus metadata and permissions so every tool sees the same datasets.

Amazon S3

Foundation of the data lake; Bronze, Silver, and Gold are usually prefixes or buckets. Cheap, durable, and the default landing zone for batch and streaming outputs.

AWS Lake Formation

Sets up and secures the lake—fine-grained table/column access, sharing across accounts. Use when many teams query the same S3 data with different entitlements.

AWS Glue Data Catalog

Central hive-style metastore: table names, columns, partitions, and file locations. Athena, Glue, EMR, and Redshift Spectrum all discover data through it.

3 · Transform & orchestrate

Turn raw files into Silver and Gold—and chain jobs reliably on a schedule or on events.

AWS Glue

Serverless Spark and Python jobs for crawl, ELT, and catalog updates. Default choice for scheduled medallion jobs and job bookmarks on incremental loads.

Amazon EMR

Managed Hadoop/Spark clusters when you need custom Spark versions, heavy shuffle, or long-running batch at scale beyond a single Glue job.

Managed Apache Flink

Stateful stream processing with windows, joins, and late data. Use to build real-time Silver features from Kinesis or MSK without managing Flink clusters.

AWS Lambda

Event-driven micro-transforms: validate uploads, split files, trigger Glue, send alerts. Use for light logic at ingest—not for large Spark workloads.

Step Functions & Amazon MWAA

Step Functions coordinates multi-step pipelines (ingest → Glue → check → notify) with retries. MWAA runs Apache Airflow when teams already use DAGs, sensors, and complex dependencies.

4 · Analyze

Query and explore curated data—ad hoc on the lake or high-performance SQL in a warehouse.

Amazon Athena

Serverless SQL directly on S3 via the Glue Catalog; pay per data scanned. Ideal for ad hoc analysis, data exploration, and lightweight Gold tables on files.

Amazon Redshift

Columnar MPP warehouse for dashboards, complex joins, and concurrent BI users. Often hosts Gold marts; can query S3 via Spectrum for lakehouse patterns.

Amazon OpenSearch

Search and log analytics on semi-structured text and JSON. Use for operational dashboards, full-text search, and near-real-time observability over streaming indexes.

5 · Consume

Deliver insights to people, models, and applications—downstream of Gold or curated marts.

Amazon QuickSight

Managed BI for KPI dashboards and self-serve charts on Athena, Redshift, and S3. Use for executive reporting without standing up a separate BI server fleet.

Amazon SageMaker

Train and deploy ML models on features from Gold tables or the lake. Data engineers feed curated datasets; scientists experiment without copying sensitive raw Bronze widely.

APIs & operational apps

API Gateway, AppSync, or event buses expose metrics and alerts to products. Use when dashboards are not enough—e.g. fraud scores, inventory triggers, or customer-facing stats.

Module 4

Cloud economics

Cloud economics is how you trade money for flexibility. Instead of buying servers upfront (capital expense), you rent capacity by the hour, gigabyte, or query (operating expense). The bill follows real usage—so architecture choices directly shape cost: what you store, how long you keep it, when compute runs, and how much data each job reads.

Pay for what you use

Glue, Lambda, and Athena bill when work happens; an idle Redshift or EMR cluster still charges while it waits. Data engineering favors elastic patterns—batch jobs that start and stop, serverless SQL for ad hoc questions—unless steady 24/7 load justifies a always-on warehouse.

Unit costs you can reason about

Think in meters: dollars per TB-month in S3, per DPU-hour in Glue, per TB scanned in Athena, per node-hour in Redshift. A pipeline is “cheap” or “expensive” only relative to volume and frequency—10 GB daily is not the same problem as 10 TB.

Storage is cheap; mistakes are not

Raw Bronze can sit affordably on object storage, but reading the wrong data is costly—full-table scans, tiny files, and uncompressed CSV inflate compute bills. Columnar formats, partitions, and lifecycle rules (move old Bronze to Glacier, expire scratch data) keep storage and scan costs aligned with value.

Design for cost, not only speed

Economics is a product requirement: partition keys that match filters, incremental loads with job bookmarks, idempotent retries, and tagging for cost allocation by team or environment. FinOps tracks the bill; data engineers change the pipelines that generate it.

Rule of thumb for this course: store once in Bronze, transform with the smallest engine that fits the SLA, query only curated partitions, and turn off what nothing is using.

Interview practice

E · Bronze, Silver, Gold for a store manager

Bronze keeps every receipt; Silver fixes typos and duplicates; Gold is today’s sales total AskShelf reads.

M · Why ELT on AWS?

Cheap S3 holds raw data; Glue/Athena reshape without re-hitting Store-12 POS.

H · Bill doubled, flat data — check what first?

Idle Redshift/EMR, Athena scan volume, forgotten NAT or duplicate Glue runs.
